    # 📖 System Design — Top 30 Theory Questions (Revision Notes)

    ## 🔥 CORE FUNDAMENTALS (1–10)

    **1. What is System Design?**
    Designing scalable, reliable, and efficient systems to handle real-world traffic.

    **2. HLD vs LLD?**
    HLD → overall architecture (services, DB, flow)
    LLD → detailed design (classes, logic, code structure)

    **3. Functional vs Non-Functional Requirements?**
    Functional → what system does
    Non-functional → performance, scalability, reliability

    **4. What is Scalability?**
    Ability of a system to handle increased load by adding resources.

    **5. Vertical vs Horizontal Scaling?**
    Vertical → increase machine power
    Horizontal → add more machines (preferred)

    **6. What is Load Balancer?**
    Distributes incoming traffic across multiple servers.

    **7. What is CDN?**
    Caches content closer to users to reduce latency.

    **8. What is Caching?**
    Storing frequently accessed data for faster retrieval.

    **9. What is CAP Theorem?**
    Consistency, Availability, Partition Tolerance → only 2 can be guaranteed.

    **10. SQL vs NoSQL?**
    SQL → structured, ACID, strong consistency
    NoSQL → flexible schema, scalable, eventual consistency

    ---

    ## ⚡ ARCHITECTURE & SYSTEM FLOW (11–20)

    **11. Monolith vs Microservices?**
    Monolith → single application
    Microservices → independent services

    **12. What is API Gateway?**
    Single entry point for all client requests.

    **13. What is Event-Driven Architecture?**
    Systems communicate via events asynchronously.

    **14. What is Message Queue?**
    Handles asynchronous processing (Kafka, RabbitMQ).

    **15. What is Sharding?**
    Splitting database across multiple machines.

    **16. What is Replication?**
    Copying data across servers for reliability.

    **17. What is Consistent Hashing?**
    Distributes data across nodes with minimal reshuffling.

    **18. What is Rate Limiting?**
    Restricting number of requests per user/system.

    **19. What is Idempotency?**
    Same request produces same result (important for retries).

    **20. What is Circuit Breaker?**
    Stops repeated failures to prevent system overload.

    ---

    ## 🚀 PERFORMANCE & REAL-WORLD (21–30)

    **21. Cache Aside vs Write Through?**
    Cache Aside → app manages cache
    Write Through → cache updated along with DB

    **22. What is LRU Cache?**
    Removes least recently used items first.

    **23. What is Eventual Consistency?**
    Data becomes consistent over time.

    **24. Latency vs Throughput?**
    Latency → response time
    Throughput → number of requests handled

    **25. What is Fault Tolerance?**
    System continues working despite failures.

    **26. What is High Availability?**
    System remains accessible with minimal downtime.

    **27. SLA vs SLO vs SLI?**
    SLA → agreement
    SLO → target
    SLI → actual measurement

    **28. REST vs GraphQL?**
    REST → fixed endpoints
    GraphQL → flexible queries

    **29. Polling vs WebSockets?**
    Polling → repeated requests
    WebSockets → real-time communication

    **30. What are Trade-offs in System Design?**
    Balancing decisions like:

    * Consistency vs Availability
    * Latency vs Throughput
    * Cost vs Performance

    # 🎯 System Design — Top 30 Tricky Questions (With Answers)
    ## 🔥 BASICS BUT TRICKY (1–10)

    **1. Can we scale a system without caching?**
    Yes, but performance will degrade significantly and cost increases.

    **2. Is NoSQL always better for scalability?**
    No. SQL can scale with sharding and replication.

    **3. Can we use only cache without DB?**
    No. Cache is temporary; DB is the source of truth.

    **4. Is eventual consistency always acceptable?**
    No. Not for banking, payments, or critical systems.

    **5. Can a load balancer become a bottleneck?**
    Yes. Solution → multiple load balancers.

    **6. Is microservices always better than monolith?**
    No. Adds complexity; not needed for small systems.

    **7. Can CDN replace backend servers?**
    No. CDN only serves static or cached content.

    **8. Is vertical scaling enough?**
    No. Limited by hardware capacity.

    **9. Can we avoid database indexing?**
    Possible, but queries become slow at scale.

    **10. Is REST always better than GraphQL?**
    No. Depends on use case.

    ---

    ## ⚡ SCALING & PERFORMANCE (11–20)

    **11. What happens if cache fails?**
    Fallback to DB → possible performance hit.

    **12. Can replication replace backups?**
    No. Replication copies errors too; backups are needed.

    **13. What if DB becomes bottleneck?**
    Use caching, read replicas, sharding.

    **14. Can we shard without consistent hashing?**
    Yes, but rebalancing becomes difficult.

    **15. What if one microservice fails?**
    Use circuit breaker + retries + fallback.

    **16. Can message queues guarantee delivery?**
    Depends (at least once / exactly once / at most once).

    **17. What happens if queue grows infinitely?**
    System delay → need backpressure handling.

    **18. Can we process everything synchronously?**
    No. Async improves scalability.

    **19. What if API is called multiple times (retry)?**
    Use idempotency.

    **20. Can we avoid rate limiting?**
    No. System can be abused or overloaded.

    ---

    ## 🚀 REAL-WORLD EDGE CASES (21–30)

    **21. What if two users update same data?**
    Use locking / versioning.

    **22. What if network fails between services?**
    Retries + timeout + fallback.

    **23. What if cache and DB mismatch?**
    Use cache invalidation strategies.

    **24. What if traffic suddenly spikes?**
    Auto-scaling + load balancing.

    **25. Can we guarantee zero downtime?**
    No. But can minimize with redundancy.

    **26. What if logs grow too large?**
    Use log rotation + centralized logging.

    **27. Can we delete old data anytime?**
    Depends on compliance and business rules.

    **28. What if one region goes down?**
    Use multi-region deployment.

    **29. Can we always optimize for performance?**
    No. Trade-offs with cost and complexity.

    **30. What if system becomes too complex?**
    Simplify design; avoid over-engineering.

    ---

    # 🧠 How to Handle Tricky Questions

    * Stay calm
    * Don’t rush answer
    * Explain trade-offs
    * Say “depends on use case” when needed

    ---
