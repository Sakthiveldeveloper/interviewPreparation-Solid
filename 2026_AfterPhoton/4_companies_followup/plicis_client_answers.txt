1.Able to create a nested components and write clean JSX markup(uses automic design principle)
    Atomic Design in React is a methodology for structuring user interfaces by breaking them down into five distinct, hierarchical levels—Atoms, Molecules, Organisms, Templates, and Pages—inspired by chemistry. It aligns perfectly with React’s component-based architecture to promote reusability, maintainability, and scalability. 
    Creating a clean, nested structure using Atomic Design helps keep your JSX readable and your UI scalable. Here is how you can break it down: 
    1. Atoms (The smallest building blocks)
    These are basic tags that can’t be broken down further without losing their function. 
    jsx
    // src/components/atoms/Button.jsx
    export const Button = ({ label, onClick, type = "button" }) => (
    <button className={`btn btn-${type}`} onClick={onClick}>
        {label}
    </button>
    );

    // src/components/atoms/Input.jsx
    export const Input = ({ placeholder, value, onChange }) => (
    <input 
        className="input-field"
        placeholder={placeholder} 
        value={value} 
        onChange={onChange} 
    />
    );
    Use code with caution.

    2. Molecules (Groups of atoms)
    These are simple groups of atoms functioning together as a unit. 
    jsx
    // src/components/molecules/SearchBar.jsx
    import { Button } from "../atoms/Button";
    import { Input } from "../atoms/Input";

    export const SearchBar = ({ onSearch }) => (
    <div className="search-bar">
        <Input placeholder="Search items..." />
        <Button label="Search" onClick={onSearch} type="primary" />
    </div>
    );
    Use code with caution.

    3. Organisms (Complex UI sections)
    These are distinct sections of an interface made of molecules and atoms. 
    jsx
    // src/components/organisms/Header.jsx
    import { SearchBar } from "../molecules/SearchBar";
    import { Button } from "../atoms/Button";

    export const Header = () => (
    <header className="main-header">
        <div className="logo">MyBrand</div>
        <SearchBar />
        <Button label="Login" type="secondary" />
    </header>
    );
    Use code with caution.

    Tips for Clean JSX:
    Destructure Props: Keeps your code concise and identifies dependencies immediately.
    Logical Nesting: If a component grows beyond 100 lines, it’s likely time to move a chunk into a new Molecule or Organism.
    Fragment Usage: Use <> ... </> to avoid "div soup" (unnecessary wrapper elements).

4.Able to style the components using the trational Css or Css in JS?
    In an interview, explain that choosing between Traditional CSS and CSS-in-JS depends on the project's scale and your team's preference for separation of concerns vs. component-scoped logic.
    1. Traditional CSS (External Stylesheets)
    This is the classic approach where styles live in .css or .scss files.
    How it works: You import the file and use className.
    Pros: Familiar, works with all tools, better performance (no runtime overhead).
    Cons: Risk of "Global Namespace" collisions (one class accidentally styling another component).
    jsx
    // Button.css
    .btn-primary { background: blue; }

    // Button.jsx
    import './Button.css';
    const Button = () => <button className="btn-primary">Click</button>;
    Use code with caution.

    Note: CSS Modules (Button.module.css) are the modern fix for global collisions.
    2. CSS-in-JS (Styled Components / Emotion)
    Styles are written directly inside JavaScript files using tagged template literals.
    How it works: Styles are scoped automatically to the component.
    Pros: Dynamic styling (styles change based on props), no global naming conflicts, dead code elimination.
    Cons: Small performance hit at runtime, requires extra libraries.
    jsx
    // Button.jsx
    import styled from 'styled-components';

    const StyledButton = styled.button`
    background: ${props => props.primary ? 'blue' : 'gray'};
    color: white;
    `;

    const Button = ({ primary }) => <StyledButton primary={primary}>Click</StyledButton>;
    Use code with caution.

    Which one to choose?
    Traditional CSS/Modules: Best for performance-critical apps or teams coming from a web design background.
    CSS-in-JS: Best for complex design systems where styles need to react heavily to component state.
    Traditional CSS: This involves writing styles in separate .css files and linking them to your components, typically using class names. It maintains a separation of concerns between structure (HTML/JSX), styling (CSS), and behavior (JavaScript), and the files can be cached by the browser for performance. However, styles are global by default, which can lead to naming conflicts in large projects.
    CSS-in-JS: This is a technique where you write your CSS code directly within your JavaScript files, using libraries like Styled Components or Emotion. Styles are automatically scoped to the component, preventing conflicts, and you can use JavaScript logic for dynamic styling (e.g., changing a color based on a prop or state). The styles are tightly coupled with their components, which can improve maintainability

6.Able to render component in the loop and understand best practice related to Key attributes
    1. Rendering Components in a Loop
    Use the .map() method to transform an array of data into an array of JSX elements.
    jsx

        {users.map((user) => (
        <UserItem key={user.id} name={user.name} />
        ))}
    </ul>
    );
    Use code with caution.

    2. The "Key" Attribute: Why it Matters
    The key is a unique string or number that helps React’s reconciliation algorithm identify which items have changed, been added, or been removed.
    Stability: Keys help React "remember" which DOM element belongs to which data object.
    Performance: Instead of re-rendering the entire list, React only updates the specific element that changed.
    3. Best Practices for Keys
    Use Unique IDs: Always prefer stable, unique identifiers from your data (e.g., user.id or product.sku).
    Avoid Using Index: Never use the array index (map((item, index) => ... )) as a key if the list can be reordered, filtered, or deleted. This causes UI bugs (like inputs losing focus or showing wrong data).
    Keys Must Be Stable: Don't generate random keys (like Math.random()) during render. This forces React to recreate the entire list on every render.
    Siblings Only: Keys only need to be unique among siblings, not globally across the entire app.

7.Able to create form and handle submitting data use Ajax?
    To explain this in an interview, focus on Controlled Components and using the Fetch API (or Axios) to handle the data flow without refreshing the page.
    1. Controlled Components
    In React, "Controlled Components" mean the form data is handled by the component state (useState). Every input has a value linked to state and an onChange handler to update it.
    2. Handling the Submit Event
    You must use event.preventDefault() to stop the browser's default behavior of reloading the page, then use an Async/Await function to send the AJAX request.
    Interview-Ready Code Example:
    jsx
    import React, { useState } from 'react';

    const ContactForm = () => {
    const [formData, setFormData] = useState({ name: '', email: '' });

    const handleChange = (e) => {
        // Dynamically update state based on input 'name' attribute
        setFormData({ ...formData, [e.target.name]: e.target.value });
    };

    const handleSubmit = async (e) => {
        e.preventDefault(); // Stop page reload
        
        try {
        const response = await fetch('https://api.example.com', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify(formData),
        });

        if (response.ok) alert('Data submitted successfully!');
        } catch (error) {
        console.error('Submission error:', error);
        }
    };

    return (
        <form onSubmit={handleSubmit}>
        <input name="name" value={formData.name} onChange={handleChange} placeholder="Name" />
        <input name="email" value={formData.email} onChange={handleChange} placeholder="Email" />
        <button type="submit">Send Data</button>
        </form>
    );
    };
    Use code with caution.

    Key Interview Points:
    Prevent Default: Mention e.preventDefault()—it's the first thing interviewers look for.
    Loading States: Mention adding a loading state (boolean) to disable the submit button while the request is in progress to prevent duplicate submissions.
    Validation: Briefly mention that you can validate state (e.g., formData.email.includes('@')) before calling the API.

9.Able to write front end unit test cases for react component using enzyme/RTL (not snapshot)
    In an interview, prioritize React Testing Library (RTL) over Enzyme, as it is the current industry standard and focuses on how users interact with the app rather than internal implementation details.
    1. The Core Philosophy
    RTL: Tests behavior (e.g., "Does the button click call the function?"). It encourages accessible code by using queries like getByRole or getByText.
    Enzyme: Tests implementation (e.g., "Does the state change to true?"). This is now considered "brittle" because if you rename a state variable, the test breaks even if the feature still works.
    2. Essential RTL Test Case (The "Three As")
    Explain the AAA pattern: Arrange (render), Act (interact), Assert (check results).
    jsx
    import { render, screen, fireEvent } from '@testing-library/react';
    import ContactForm from './ContactForm';

    test('submits the form with user input', () => {
    // 1. Arrange
    const mockSubmit = jest.fn();
    render(<ContactForm onSubmit={mockSubmit} />);

    // 2. Act
    const input = screen.getByLabelText(/email/i);
    const button = screen.getByRole('button', { name: /submit/i });

    fireEvent.change(input, { target: { value: 'test@example.com' } });
    fireEvent.click(button);

    // 3. Assert
    expect(mockSubmit).toHaveBeenCalledTimes(1);
    expect(mockSubmit).toHaveBeenCalledWith({ email: 'test@example.com' });
    });
    Use code with caution.

    3. Key Interview Points
    Avoid Snapshots: Mention that you prefer explicit assertions (like expect(element).toBeInTheDocument()) because snapshots often grow too large to review properly and hide real bugs.
    Mocking APIs: Use jest.mock() or libraries like MSW (Mock Service Worker) to intercept AJAX calls so your unit tests don't hit a real server.
    User Event: Mention that using @testing-library/user-event is even better than fireEvent because it simulates full browser interactions (like focus and keydown events).

10.Able to demonstrate handling error using error bounderies
    In an interview, explain that Error Boundaries are special React components that catch JavaScript errors anywhere in their child component tree, log those errors, and display a fallback UI instead of crashing the entire app (the "white screen of death").
    1. The Core Concept
    Error Boundaries only catch errors in rendering, lifecycle methods, and constructors.
    They do not catch errors in event handlers, asynchronous code (like fetch), or server-side rendering.
    2. Implementation (Class Component)
    Currently, Error Boundaries must be Class Components because they require the lifecycle methods getDerivedStateFromError and componentDidCatch.
    jsx
    import React from 'react';

    class ErrorBoundary extends React.Component {
    constructor(props) {
        super(props);
        this.state = { hasError: false };
    }

    // 1. Update state so the next render shows the fallback UI
    static getDerivedStateFromError(error) {
        return { hasError: true };
    }

    // 2. Log the error to an error reporting service (e.g., Sentry)
    componentDidCatch(error, errorInfo) {
        console.error("ErrorBoundary caught an error", error, errorInfo);
    }

    render() {
        if (this.state.hasError) {
        return <h1>Something went wrong. Please refresh.</h1>; // Fallback UI
        }

        return this.props.children; 
    }
    }

    export default ErrorBoundary;
    Use code with caution.

    3. Usage in JSX
    Wrap specific parts of your app so a failure in one section (like a sidebar) doesn't break the whole page.
    jsx
    <ErrorBoundary>
    <Header />
    <ErrorBoundary>
        <MainContent /> {/* If this fails, Header still works */}
    </ErrorBoundary>
    <Footer />
    </ErrorBoundary>
    Use code with caution.

    Key Interview Points:
    Granular Placement: Mention that it's a best practice to have multiple small Error Boundaries (e.g., one for a widget, one for a page) rather than just one at the top.
    Fallback Props: Mention that you can pass a custom fallback prop to the boundary to make it reusable for different UI sections.
    Functional Alternative: Mention that for functional components, the library react-error-boundary is the industry standard for a more "modern" hook-like approach.

11.Has work with Various rendering in React and Next js, eg, SSR, CSR, SSG, ISR, able to define them
    The 4 Main Rendering Strategies
    CSR (Client-Side Rendering): The browser downloads a minimal HTML shell and then uses JavaScript to fetch data and render the UI.
    Use Case: Highly interactive dashboards or private profile pages where SEO doesn't matter.
    SSR (Server-Side Rendering): The server generates the full HTML for the page on every single request.
    Use Case: Pages that need real-time data and high SEO, like a personalized news feed or search results.
    SSG (Static Site Generation): The HTML is generated once at build time and served instantly from a CDN.
    Use Case: Marketing pages, blogs, or documentation that rarely changes.
    ISR (Incremental Static Regeneration): A hybrid that lets you update static pages after the site is deployed, without a full rebuild.
    Use Case: E-commerce product pages where you want the speed of SSG but need to update prices or stock every few minutes.

    Purpose: Remembers the result of a function. It only re-runs the function when its dependencies change.
    Use Case: Filtering a massive list, performing complex math, or transforming data before rendering.
    Simple Demo:
    jsx

    return performHeavyCalculation(data); 
    }, [data]); // Only recalculates if 'data' changes

    Purpose: Remembers the function instance itself. In JavaScript, functions are recreated on every render; useCallback prevents this.
    Use Case: Passing a callback function to a memoized child component (React.memo) to prevent that child from re-rendering needlessly.
    Simple Demo:
    jsx
    const handleItemClick = useCallback((id) => {
    console.log("Clicked:", id);
    }, []); // Function stays the same for the full lifecycle
    Use code with caution.

    3. Key Differences
    Feature	useMemo	useCallback
    Returns	The result of the function (Value/Object)	The function itself
    Goal	Avoid expensive re-calculations	Avoid unnecessary child re-renders
    Analogy	Storing the answer to a math problem	Keeping the same physical key to a door
    Best Practices for Interviews:
    Don't Overuse: Explain that memoization has a cost (memory and complexity). Only use it if you notice a performance lag or to fix broken useEffect dependencies.

    In an interview, explain state management as a spectrum of complexity. You choose the tool based on how many components need the data and how often that data changes.
    1. The State Management Hierarchy
    Local State (useState / useReducer): Best for data that stays inside one component (e.g., a form input or a toggle switch).
    Global Context (Context API): Best for "low-frequency" updates like Theming, User Auth, or Language settings. It avoids prop-drilling but can cause re-render issues if used for high-frequency data.
    External Stores (Redux, Zustand, Recoil): Best for "high-frequency" or complex data that many far-apart components need to access (e.g., a shopping cart or a real-time chat).
    2. Redux (The Industry Standard)
    Redux is a predictable state container based on the principle of a "Single Source of Truth."
    How it works: You dispatch an Action → a Reducer processes it → the Store updates → the UI re-renders.
    Pros: Excellent debugging tools (Redux DevTools), strict pattern makes it easy for large teams to collaborate, and handles complex side effects well with Redux Toolkit (RTK).
    Cons: High boilerplate (lots of code to write) and a steeper learning curve compared to newer libraries.
    3. Modern Alternatives
    Zustand: A small, fast, and scalable state management solution. It’s much simpler than Redux and uses hooks directly.
    React Query (TanStack Query): Crucial Point: Most "state" in apps is just Server Cache (data from an API). React Query handles caching, loading states, and re-fetching automatically, often eliminating the need for Redux entirely.
    Comparison Table for Interviews
    Tool	Complexity	Best For
    useState	Low	UI Toggles, Form Inputs
    Context API	Medium	Static Data (Theme, Auth)
    Redux (RTK)	High	Complex Enterprise Apps
    Zustand	Medium	Modern, lightweight Global State
    React Query	Medium	Server Data (API Caching)
    Golden Rule for Interview: "I prefer to keep state as local as possible. I use React Query for server data, and only move to Redux or Zustand if the client-side logic becomes too complex for the Context API."
